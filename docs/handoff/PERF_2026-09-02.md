# Making the gate faster — what was actually slow

**2 Sep 2026.** Prompted by "can the cost be better?", which turned out to be the right
question asked of the wrong number.

## The mistake in the first benchmark

The first A/B run reported the gate costing ~25ms of server time. That number was wrong, and
wrong in an instructive way: **it was measuring a machine waking up, not a gate deciding.**

`fly.toml` sets `auto_stop_machines = "suspend"` with `min_machines_running = 1`. One machine
stays warm; the second suspends and wakes under load. A probe that does not warm up first can
land on a waking machine and attribute the wake-up to whatever it was measuring.

Measured on a warm machine, in the datacentre, with `performance.now()`:

| | p50 | p95 |
|---|---|---|
| `GET /healthz` (an empty request) | 2.38ms | 7.19ms |
| `POST /v1/effects/begin` (new effect) | **2.25ms** | 3.51ms |
| `POST /v1/effects/begin` (replay) | **2.31ms** | 4.06ms |

**The gate is indistinguishable from an empty HTTP request.** The comment already in `fly.toml`
— *"a cold start in front of every side effect turns a 2ms gate into a multi-second one"* — was
exactly right, and the first benchmark had measured the cold start.

## What was genuinely slow, and is now fixed

An audit of the request path counted the round trips rather than guessing at them. The gate was
never CPU-bound — Ed25519 signing, canonicalization and hashing total ~0.2ms — it was making
**sequential awaited database round trips that cannot overlap**.

| Fix | Round trips saved | Path |
|---|---|---|
| **Authentication ran twice per request.** The `v1` onRequest hook authenticates so the rate limiter knows the caller's plan; each route guard then authenticated the identical string again. The guard reuses the hook's context, but only on a byte-identical token — the hook reads `Authorization` while `bearer()` also accepts `x-api-key`, so the two can legitimately hold different credentials. | 1 query + HMAC + write | both |
| **A duplicate asked about the same row three times**: a pre-check selecting `id`, an INSERT guaranteed to conflict, and a re-SELECT to find out what the row said. The pre-check now reads the whole row under `FOR UPDATE`. | 2 queries | replay |
| **Opening a transaction was two round trips** before it had done anything. `BEGIN` and the `SET LOCAL` timeouts now travel in one message. | 1 round trip | both |
| **The surge baseline was read for most new effects to compute a number nothing read.** `observed` is used only inside the `ceiling !== null` branch, and no ceiling is the default. | 1 query | new |

Measured locally, where there is no network or suspend to hide behind:

| | before | after | |
|---|---|---|---|
| replay | 2.02ms | **1.40ms** | −31% |
| new effect | 3.01ms | **2.47ms** | −18% |
| queries per replay | 16 | **9** | |

## End to end, from a laptop

The A/B benchmark, median of three runs, against production:

| | before | after |
|---|---|---|
| gate p50 | 76–129ms | **56–62ms** |
| gate **p95** | 528–1428ms | **117–119ms** |
| gate max | 1556–1650ms | **165–187ms** |

The p95 is the one that moved: **roughly 12x**. Most of that is the round trips removed; some is
that the machine is now warm, which is precisely the confound described above and is stated
rather than claimed as credit.

**Correctness was identical in every run before and after** — 13 duplicate refunds prevented,
$3,120 not lost, deterministic because the failure sequence is seeded.

## The gate now pays for itself in time, not only in money

Across three runs after the change, the gated job finished **faster** than the ungated one, by
64–269ms per job. That is not the gate being free; it is a prevented duplicate being worth more
than the gate costs. Each duplicate the gate refuses is a vendor call that never happens — and
in this workload a failing vendor call costs a 4-second timeout, against ~60ms to ask permission.

**This result depends on the vendor being slow.** Against a fast vendor the gate would add net
time. Stated because an earlier run of this benchmark showed the same effect, I nearly reported
it, and the next run reversed the sign — it was variance then, and only became a real finding
when it held across three runs with a mechanism that explains it.

## Not done, and why

- ~~`reserveSpend` issues 9 sequential statements~~ **Done.** Now one
  `INSERT … SELECT unnest(…) WITH ORDINALITY … ORDER BY ord … ON CONFLICT DO UPDATE … RETURNING`.
  Nine round trips became one; budget enforcement now costs **0.25ms** on top of a begin, which
  is a single round trip.

  The rewrite is safe because of *where it runs*, not because of anything clever in the SQL.
  `reserveSpend` is inside begin's transaction and a `BudgetExceeded` propagates out as an
  `ApiError` that nothing catches in a way that lets the transaction commit — so the increment
  this statement performs is undone by the same rollback that refuses the effect.
  Increment-then-validate is therefore externally identical to lock-validate-increment.

  `ORDER BY s.ord` is load-bearing: rows are locked in the order the subquery produces them, and
  a fixed order across concurrent callers is what stops two reservations deadlocking. And the
  materialise-before-lock rule is *strengthened*, not weakened — one atomic upsert has no window
  in which the row is absent and `SELECT … FOR UPDATE` would lock nothing, which is the race the
  old three-step dance existed to prevent.

  `test/integration/budget-reserve.test.ts` was written and made green against the **old**
  implementation first, then run unchanged against the new one. It asserts the properties rather
  than the mechanism: a refusal records nothing, failing one scope leaves the others untouched,
  the error reports spend *before* the attempt, and twelve concurrent reservations cannot
  collectively exceed a ceiling.
- **`meterEffect` re-locks the `workspaces` row** the transaction already holds. One round trip,
  low risk, needs the read folded into the write.
- **The receipt INSERT could ride on the metering UPDATE** as a CTE, staying in the same
  transaction. One round trip.
- **`last_used_at` writes could be buffered in-process** the way `activity.ts` already buffers
  counters. Costs pool connections rather than latency, and `DB_POOL_MAX` is 10.
- **Caching authentication across requests was rejected.** A revoked key must stop working, and
  a TTL is the real bound — invalidation does not cross machines.

## What keeps this from regressing

`test/integration/hot-path.test.ts` asserts the round-trip counts, not the timings. Latency
assertions are flaky on a loaded runner and prove nothing; round trips are a property of the
code and are what the latency is made of.

Writing that test caught two errors in my own measurement, both worth knowing about:

- Watching only `pool.query` misses everything inside a transaction, which silently turns every
  "this query does not happen" assertion into one that passes against an empty list.
- Watching the pool *and* its clients double-counts, because `pool.query()` checks out a client
  and calls `client.query()`. That reads exactly like a duplicate query in the code, and sent me
  looking for a bug that was in the instrument.
